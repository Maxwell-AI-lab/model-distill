# Long-horizon Planning Distillation — 技术方案

## 一、问题定义

### 1.1 什么是长程任务规划能力？

```
用户: "帮我从北京搬到上海，包括找房子、搬家公司、转户口、孩子转学"

大模型的规划过程:
┌─────────────────────────────────────────────┐
│ 任务分解:                                    │
│   阶段1: 前期准备 (2周前)                    │
│   ├── 1.1 确定上海居住区域                   │
│   ├── 1.2 联系上海房东/中介看房              │
│   ├── 1.3 了解上海户口政策                   │
│   └── 1.4 联系目标学校了解转学要求           │
│                                              │
│   阶段2: 搬迁执行 (1周前)                    │
│   ├── 2.1 确定房子后签合同                   │
│   ├── 2.2 联系搬家公司比价                   │
│   ├── 2.3 办理北京这边的水电宽带停机         │
│   └── 2.4 北京户口迁出手续                   │
│                                              │
│   阶段3: 落地安顿 (搬家后)                   │
│   ├── 3.1 上海户口迁入                       │
│   ├── 3.2 孩子入学手续                       │
│   ├── 3.3 水电宽带开通                       │
│   └── 3.4 更新各种地址信息                   │
│                                              │
│ 依赖关系: 2.1 → 2.2; 1.3 → 2.4 → 3.1;       │
│           1.4 → 3.2; ...                     │
│                                              │
│ 风险预案:                                    │
│   - 房子没找好 → 先住短租公寓                │
│   - 户口迁出受阻 → 先办暂住证                │
└─────────────────────────────────────────────┘
```

这就是长程规划——**给定一个复杂目标，模型能分解、排序、识别依赖、处理异常。**

### 1.2 为什么这是蒸馏的难点？

| 挑战 | 说明 |
|------|------|
| **不是模式匹配** | 规划能力需要真正的推理，不能靠"背答案" |
| **组合爆炸** | 任务空间巨大，无法覆盖所有情况 |
| **上下文长** | 规划过程本身就很长，小模型容易遗忘 |
| **需要自我修正** | 好的规划器会检查自己的计划是否合理 |
| **评估困难** | 什么叫"好的规划"？标准不清晰 |

## 二、蒸馏方案总览

### 2.1 核心思路

```
不蒸馏"通用规划能力"，而是蒸馏"特定领域的规划范式"

大模型: 通用规划器 (能处理任意任务)
    ↓ 蒸馏
小模型: 领域规划器 (在你的场景内做好规划)
```

### 2.2 四阶段蒸馏法

```
┌──────────────────────────────────────────────────────────────┐
│                    四阶段蒸馏方案                              │
│                                                              │
│  阶段 1: 规划范式学习 (Planning Pattern Learning)            │
│  ── 让小模型学会"什么是好的计划"                              │
│  ── SFT: Teacher 生成 (任务→计划) 对                         │
│                                                              │
│  阶段 2: 分步执行学习 (Step-by-Step Execution)               │
│  ── 让小模型学会"怎么一步步执行计划"                          │
│  ── SFT: Teacher 演示 (步骤→动作) 序列                       │
│                                                              │
│  阶段 3: 偏好对齐 (Preference Alignment)                     │
│  ── 让小模型学会"区分好计划和差计划"                          │
│  ── DPO: Teacher 标注 (好计划 vs 差计划)                     │
│                                                              │
│  阶段 4: 自我反思 (Self-Reflection)                          │
│  ── 让小模型学会"发现自己计划的错误"                          │
│  ── SFT: Teacher 生成 (计划→审查→修正)                       │
└──────────────────────────────────────────────────────────────┘
```

## 三、详细设计

### 3.1 数据 Schema — 标准化长程任务表示

这是整个方案的**基础设施**。我们需要一套统一的格式来表示规划任务：

```python
# 长程规划任务的标准表示
{
    "task_id": "unique_id",
    "domain": "logistics",           # 领域
    "complexity": "high",            # low / medium / high
    "task_description": "从北京搬到上海的完整方案",

    # 目标分解 — 树状结构
    "plan": {
        "phases": [
            {
                "phase_id": "P1",
                "name": "前期准备",
                "timeline": "搬家前2周",
                "steps": [
                    {
                        "step_id": "S1.1",
                        "action": "确定上海居住区域",
                        "prerequisites": [],
                        "expected_outcome": "锁定2-3个目标区域",
                        "resources": ["安居客", "链家APP"],
                        "risk": "预算不足",
                        "fallback": "考虑合租或偏远区域"
                    },
                    {
                        "step_id": "S1.2",
                        "action": "联系中介看房",
                        "prerequisites": ["S1.1"],    # 依赖 S1.1
                        "expected_outcome": "确定房源",
                        ...
                    }
                ]
            },
            ...
        ]
    },

    # 依赖图 — 步骤间的依赖关系
    "dependencies": {
        "S1.1": [],
        "S1.2": ["S1.1"],
        "S2.1": ["S1.2"],
        "S2.4": ["S1.3"],
        ...
    },

    # 风险评估
    "risks": [
        {
            "step": "S1.2",
            "risk": "找不到合适的房子",
            "probability": "medium",
            "impact": "high",
            "mitigation": "提前准备3个备选区域"
        }
    ],

    # Teacher 元信息
    "source_model": "deepseek-reasoner",
    "planning_time_seconds": 12.5
}
```

### 3.2 阶段 1: 规划范式学习

**目标**：让小模型学会"看到任务 → 产出结构化计划"

**数据生成方法：**

```
Step 1: 构造任务种子
─────────────────────
按领域批量构造任务描述:

领域种子:
├── 日常事务:  "策划一次家庭旅行"、"装修房子"、"准备一场考试"
├── 工作场景:  "组织一场100人会议"、"上线一个新功能"、"处理一次线上故障"
├── 项目管理:  "从0搭建一个电商系统"、"完成一次数据迁移"
├── 运维SRE:   "排查数据库慢查询"、"处理线上OOM故障"
├── 生活规划:  "一个月内减肥5斤"、"筹备婚礼"
└── 多步推理:  "分析这篇论文的方法是否可行"、"对比三个技术方案的优劣"

Step 2: Teacher 生成计划
─────────────────────
对每个任务，让 Teacher 输出完整的结构化计划:

System: "你是一个专业的任务规划专家。请为以下任务制定详细计划。"

User: "任务: 组织一场100人的技术会议
       要求: 
       1. 分阶段列出所有步骤
       2. 标注步骤间的依赖关系
       3. 识别关键风险和预案
       4. 给出合理的时间线
       请严格按 JSON 格式输出。"

Step 3: 多 Teacher 对比增强
─────────────────────
同一任务，分别用 Kimi / GLM / DeepSeek 生成计划:

Task X → Kimi Plan A
      → GLM Plan B
      → DeepSeek Plan C

→ 取三个计划的并集（互补），用最好的一个做 SFT 标签
→ 用较差的做 DPO 的 rejected
```

**数据量估计：**
- 每个领域 100~500 个任务种子
- 每个任务 3 个 Teacher 各生成 1 条
- 预计产出 3,000~15,000 条高质量规划数据

### 3.3 阶段 2: 分步执行学习

**目标**：让小模型学会"按计划一步步执行"

这一步把规划能力从"静态输出计划"提升到"动态执行+调整"：

```
输入: 当前状态 + 计划
输出: 下一步动作

训练数据格式:
{
    "messages": [
        {"role": "system", "content": "你是任务执行助手。根据计划和当前状态，决定下一步。"},
        {"role": "user", "content": "计划: S1 确定区域 → S2 联系中介 → S3 看房\n当前状态: S1已完成(锁定浦东), S2进行中\n问题: 中介说浦东房源少\n下一步应该做什么?"},
        {"role": "assistant", "content": "根据当前状态分析:\n1. 浦东房源偏少，可以扩大范围到闵行\n2. 建议同时联系2-3家中介\n3. 调整计划: S1 补充(增加闵行), S2 继续\n执行动作: 联系链家闵行门店 + 安排周末看房"}
    ]
}
```

**数据生成方法：**

让 Teacher 做 **"模拟执行"**（Simulated Execution）：

```
Round 1: "你刚刚确定了搬家计划，现在执行第一步..."
Round 2: "第一步完成了，但遇到了XX问题，现在怎么办..."
Round 3: "第二步因为XX原因失败了，需要调整计划..."
...
```

这样每个任务可以产出 **5~20 条** 执行序列数据。

### 3.4 阶段 3: 偏好对齐（DPO）

**目标**：让小模型学会"区分好的规划和差的规划"

```
DPO 训练数据:

{
    "prompt": "任务: 准备一次线上系统迁移",
    "chosen": "                        ← Teacher (DeepSeek-R1) 生成的优质计划
        阶段1: 评估迁移风险 →
        阶段2: 准备回滚方案 →
        阶段3: 选择低峰期 →
        阶段4: 分批迁移灰度发布 →
        阶段5: 全量迁移 → 验证 → 清理
    ",
    "rejected": "                      ← 刻意构造的劣质计划
        直接全量迁移，迁移完检查
    "
}
```

**如何生成 rejected 数据？**
1. **降级 Teacher**：用 GLM-4-Flash（免费但弱）生成低质量计划
2. **人为扰动**：打乱步骤顺序、删除关键步骤、忽略风险
3. **跨领域错配**：用运维的计划模板去回答生活问题

### 3.5 阶段 4: 自我反思

**目标**：让小模型学会"审查和修正自己的计划"

```
{
    "messages": [
        {"role": "system", "content": "你是规划审查专家。"},
        {"role": "user", "content": "请审查以下计划:\n\n任务: 上线新功能\n计划: 写代码 → 测试 → 上线\n\n"},
        {"role": "assistant", "content": "审查发现以下问题:\n\n1. 缺少代码评审环节\n   补充: 写代码 → Code Review → 测试\n\n2. 没有灰度发布策略\n   补充: 测试 → 10%灰度 → 50% → 全量\n\n3. 没有回滚方案\n   补充: 准备回滚脚本，保留旧版本镜像\n\n修正后: 写代码 → Code Review → 测试 → 准备回滚 → 10%灰度 → 50% → 全量 → 监控"}
    ]
}
```

## 四、多 Teacher 协作策略

### 4.1 各 Teacher 的规划特长

| Teacher | 规划特长 | 适合场景 |
|---------|---------|---------|
| **DeepSeek-R1** | 推理最强，CoT 质量最高 | 复杂推理规划、技术方案、代码架构 |
| **GLM-4-Plus** | 中文理解深、常识丰富 | 生活规划、客服流程、中文场景 |
| **Kimi** | 长上下文 128K | 超长规划、需要大量背景信息的任务 |

### 4.2 具体协作方案

```
┌────────────────────────────────────────────────────┐
│              多 Teacher 协作流水线                   │
│                                                    │
│  任务输入                                          │
│      │                                             │
│      ├──→ DeepSeek-R1 生成"推理骨架"               │
│      │   (它最擅长逻辑推理和步骤分解)               │
│      │                                             │
│      ├──→ GLM-4-Plus 补充"中文细节"                │
│      │   (对每个步骤做中文语境优化)                 │
│      │                                             │
│      └──→ Kimi 做"全局一致性检查"                  │
│          (长上下文，检查整体计划是否自洽)            │
│                                                    │
│  融合输出 → 最终训练数据                            │
└────────────────────────────────────────────────────┘
```

### 4.3 自动化质量打分

用 Teacher 之间互相评分：

```
DeepSeek 生成的计划 → 让 GLM 打分 (1-10)
GLM 生成的计划 → 让 Kimi 打分
Kimi 生成的计划 → 让 DeepSeek 打分

→ 分数最高的作为 SFT 训练标签 (chosen)
→ 分数最低的作为 DPO 的 rejected
```

## 五、评估方案

### 5.1 规划质量的评估维度

```
┌────────────────────────────────────────────┐
│           规划质量评估体系                   │
│                                            │
│  1. 可执行性 (Executability) 30%           │
│     每一步是否具体、可操作？                 │
│                                            │
│  2. 完整性 (Completeness) 25%              │
│     是否遗漏了关键步骤？                     │
│                                            │
│  3. 依赖正确性 (Dependency) 20%            │
│     步骤顺序和依赖关系是否合理？             │
│                                            │
│  4. 风险意识 (Risk Awareness) 15%          │
│     是否识别了潜在风险和预案？               │
│                                            │
│  5. 效率 (Efficiency) 10%                  │
│     有没有不必要的冗余步骤？                 │
└────────────────────────────────────────────┘
```

### 5.2 评估方法

| 方法 | 说明 |
|------|------|
| **LLM-as-Judge** | Teacher 按上述维度打分 |
| **执行模拟** | 在沙盒中模拟执行计划，看能否完成 |
| **人工评估** | 抽样检查 5%~10% |
| **对比基线** | 与直接用 Teacher 的计划做对比 |

## 六、实施计划

### Phase 1: 数据基础设施（1-2 周）

```
Week 1-2:
├── 定义规划数据 Schema (JSON 格式)
├── 构造任务种子库 (5~10 个领域, 每个领域 50~100 个任务)
├── 实现 Teacher 数据生成 Pipeline
│   ├── 单 Teacher 生成
│   ├── 多 Teacher 融合
│   └── 质量打分排序
└── 产出: 3,000~5,000 条结构化规划数据
```

### Phase 2: 规划能力 SFT（1 周）

```
Week 3:
├── 格式化数据为 ChatML
├── Qwen2.5-7B SFT 训练 (先用 7B，效果更容易出来)
├── 初步评估
└── 产出: 可生成基础计划的 Student 模型
```

### Phase 3: 执行+反思+DPO（2 周）

```
Week 4-5:
├── 生成执行序列数据 (模拟执行)
├── 生成反思修正数据
├── DPO 偏好对齐
├── 全方位评估
└── 产出: 完整的规划蒸馏模型
```

### Phase 4: 压缩到更小模型（1 周）

```
Week 6:
├── 7B → 1.5B 的进一步蒸馏
├── (用 7B 蒸馏后的模型当 Teacher，再教 1.5B)
├── 部署优化
└── 产出: 可部署的小模型
```

## 七、风险与应对

| 风险 | 概率 | 应对 |
|------|------|------|
| 小模型规划能力天花板低 | 高 | 聚焦垂直领域，不追求通用；考虑 7B 而非 1.5B |
| 生成数据同质化 | 中 | 多 Teacher 融合 + 数据增强（改写、扰动） |
| 评估不靠谱 | 中 | 多维评估 + 人工抽样 + 执行模拟 |
| API 成本高 | 中 | 先小规模验证(100~200条)，确认有效再放量 |
| 复杂计划超长，小模型记不住 | 高 | 分层蒸馏：先做高层计划，细节交给执行时展开 |
